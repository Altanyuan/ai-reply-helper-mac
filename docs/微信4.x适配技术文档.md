# 微信 4.x 适配技术文档

> 记录本次为「微信 AI 润色助手」适配微信 4.x 的完整技术方案、踩坑过程与验证数据。
>
> **目标版本**：微信 4.1.13.65（Qt6 重写版）
> **验证环境**：Windows 10.0.19045.5608 / Python 3.13.2 / 1920×1080 @125% 缩放

---

## 一、问题背景

用户反馈：微信升级到 4.1.13.65 后，程序**无法获取聊天信息**，弹框提示「等待 10 秒仍未检测到微信窗口」。

原始代码里窗口定位是**硬编码类名**：

```python
win = auto.WindowControl(searchDepth=1, ClassName="WeChatMainWndForPC")
if win.Exists(0, 0):
    ...
```

类名匹配不到 → `Exists()` 恒为 `False` → 10 秒后判超时。

---

## 二、根因诊断

### 2.1 第一层：主窗口类名变更

微信 3.x 使用自研 **Duilib** 框架，主窗口类名为 `WeChatMainWndForPC`；
微信 4.0 起客户端用 **Qt6 重写**，类名变为 Qt 风格。

实测确认：

```
[命中] cls='Qt51514QWindowIcon' name='微信'
       rect=(-9,-9,1929,1039)   pid=9684
```

`Qt51514QWindowIcon` 中的 `51514` 是 Qt 版本号（5.15.14），**会随微信升级的 Qt 版本变化**，因此不能写死。

### 2.2 第二层：UIA 控件完全不可读（决定性发现）

改完类名后，窗口能定位到了，但**读取不到任何内容**。逐项验证：

| 验证手段 | 微信 4.x 结果 | 对照（Electron 应用） |
|---|---|---|
| `window.GetChildren()` | **0 个控件** | 正常返回 |
| `ControlFromPoint` 网格扫描（窗口激活态） | 2240 点 → **仅 1 个**（窗口自身） | 1248 点 → **278 个**控件、21 种类型 |
| `GetFocusedControl()` 父级链 | 无法上溯到窗口内部 | 正常 |

**结论：微信 4.x（Qt6）关闭了 UIA 无障碍暴露，整个界面为自绘，Windows UI Automation 读不到任何内部控件**（输入框、消息列表、气泡全部不可见）。

这不是搜索方式或类名的问题 —— **UIA 方案在微信 4.x 上从根上不成立**。

### 2.3 关键区分：哪些功能不受影响

| 功能 | 依赖 | 微信 4.x 是否可用 |
|---|---|---|
| 草稿捕获 | `Ctrl+A` + `Ctrl+C` 键盘模拟 | ✅ **可用**（不依赖控件树） |
| 回填粘贴 | `Ctrl+A` + `Ctrl+V` 键盘模拟 | ✅ **可用** |
| 读取聊天上下文 | UIA 控件树 | ❌ 不可用 → 需 OCR |

因此最坏情况只是「缺少上下文」，润色与回填主流程不受影响，降级影响可控。

## 三、解决方案

### 3.1 架构总览

```
[热键 Ctrl+Alt+P] / [点击右下角动图]
        ↓
on_activate()  ← 加锁防重入 + COM 初始化
        ↓
_grab_wechat(timeout=10)          main.py
        ↓
  find_wechat_window()            wechat_window.py
        ↓  进程名 → 类名 → 标题启发式（三级降级）
  read_wechat_recent(n)           capturer.py
        ├─ 3.x 路径：UIA 列表直读        ← 微信 3.x（命中即返回）
        ├─ 3.x 路径：UIA 控件树扁平收集   ← 部分过渡版本
        ├─ 4.x 路径：WGC 抓窗口 + 像素锚点 + OCR   ← 微信 4.x（见 3.3）
        └─ 兜底：OCR 截屏识别            ← WGC 不可用 / 抓帧失败时
                ↓
        ocr_reader / capture_wgc           见 3.3
        polish(draft, context, cfg)         ai_client.py
                ↓
        show_choices() → paste_back()       ui.py / paste_back.py
```

### 3.2 模块职责

| 模块 | 状态 | 职责 |
|---|---|---|
| `wechat_window.py` | **新增** | 微信窗口 / 输入框 / 消息列表统一定位 |
| `capture_wgc.py` | **后续新增** | 4.x 采集：WGC 抓窗口 + 像素锚点定位消息区 + 说话人分类（见 3.3） |
| `ocr_reader.py` | **新增** | Windows 内置 OCR（带坐标识别）+ 旧截屏读取路径 |
| `capturer.py` | 改造 | 读取上下文：3.x 走 UIA 直读、4.x 走 WGC，最后兜底截屏 OCR |
| `paste_back.py` | 改造 | 复用统一定位（回填同样受类名问题影响） |
| `main.py` | 改造 | 新定位逻辑 + 错误提示三分类 + 采集开关传参 |
| `config.py` | 改造 | 新增 `ocr_context`、`capture_4x` 开关 |

### 3.3 4.x 采集方案演进：截屏 OCR → WGC 抓窗口

方案 C（截屏 OCR）能跑通，但**稳定性不够**：实际使用中会出现「有时读不到上下文」。根因有三个：

| 硬伤 | 表现 |
|---|---|
| 抓的是**屏幕矩形**（`PIL.ImageGrab`） | 窗口被遮挡、最小化、不在前台时，截到的是别的东西 |
| 提前台靠裸调 `SetForegroundWindow` | 后台线程里会被系统静默拒绝（返回 0），窗口没提上来就截图 |
| 裁剪按 `1920×1030` 基准**等比换算** | 左侧会话列表宽度基本固定、不随窗口缩放：窄窗口混入联系人名，高窗口切掉最新几条消息 |

另外，按热键那一刻就抓帧，切会话 / 来消息的滚动动画会截到半截气泡。

**新方案（与 jev-chat-windows 相同的采集思路）**：`capture_wgc.py`

```
WGC 抓窗口（被遮挡也能截、不抢前台、不打断打字）
  → 多种取帧直到「画面停稳」（SETTLE 0.25s / 上限 1.2s）
  → 像素锚点定位消息区（认面板底色与分隔线，不写死坐标、深浅主题通用）
  → 裁出消息区 → WinRT OCR（带 bounding_rect）
  → 按气泡底色 / 文字对比度分类 me / her / gray，丢掉图片里的字与灰字
  → 同一气泡多行合并 → 取最近 n 条 → 「对方：… / 我：…」文本
```

**与 3.x 的隔离（回归红线）**：`capturer.read_wechat_recent` 按**运行时能力探测**分流 ——
3.x 在 UIA 那一级命中后直接返回，**永远不进入 4.x 的采集代码**；4.x 的 WGC 只在 UIA 落空后
被调用，失败再回落旧的截屏 OCR。`tests/test_capture_split.py` 用桩把这条分流锁死
（含「3.x 命中时 WGC 一次都不许被调用」）。

#### 实现踩坑（均已实测确认）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **输入框底色比消息区更白** | 「右半边众数」取到的是底部输入框的颜色，整块定位全错 | 底色候选先取**上半部右半边**众数（那段必然是消息区）；多个候选里选「算出的消息区最靠上」的那个（不能用面积最大当判据：输入框区又高又干净） |
| 2 | `windows-capture` 2.x 强制要求两个回调 | 只注册 frame handler → `RuntimeError: on_closed Event Handler Is Not Set` | `cap.event(self.on_frame_arrived)` 与 `cap.event(self.on_closed)` 都要注册 |
| 3 | ctypes 未声明 `argtypes` | 64 位下 HWND 被当 c_int 传递，还原动作失效 | 模块级声明 `IsIconic` / `ShowWindow` / `SetWindowPos` 的 argtypes（`paste_back.py` 踩过同一个坑） |
| 4 | `ShowWindow` 还原是**异步**的 | 不等它落地就抓帧 → 全是黑帧 | 还原后轮询 `IsIconic` 直到为 False（最多 0.6s），再留 0.12s 给 DWM 出帧 |
| 5 | 最小化窗口 DWM 不渲染 | 任何截图法都拿不到画面 | 抓帧前先 `unminimize()`：`SW_SHOWNOACTIVATE` 还原 + `HWND_BOTTOM` 压底，不抢焦点 |

实测数据（本机，记事本窗口对照）：正常状态抓帧 **0.62~0.83s**、最小化后自动还原再抓 **0.80s**，
均返回有效 RGB 帧；像素锚点在合成图上还原出与实测标定一致的区域（1920×1030 下 `(378, 87, 1920, 487)`），
底色取到消息区的 `(245,245,245)` 而不是输入框的白色。

#### 依赖与代价

- 新增 `windows-capture`（abi3 wheel，Python 3.9+ 通用），它**硬依赖 opencv-python** →
  打包体积 **+约 45MB**（exe 从 ~46MB 涨到 ~90MB）。这是为稳定性付出的代价。
- OCR 后端沿用系统内置 WinRT OCR（不引入 RapidOCR / onnxruntime）：它同样带 `bounding_rect`，
  够做颜色分类，又能省下 ~60MB 和一份 Python 3.13 兼容风险。
- 开关：`config.json` 的 `capture_4x`（`wgc` 默认 / `ocr` 切回旧路径）。

## 四、关键技术实现

### 4.1 窗口定位：三级降级策略

`wechat_window.find_wechat_window()`

```
策略 1  进程名匹配    枚举 Weixin.exe / WeChat.exe 的 pid，按 pid 匹配顶层窗口
                     —— 最稳，不受类名改版影响
策略 2  类名匹配      WeChatMainWndForPC / Qt*QWindowIcon / mmui::MainWindow
                     —— Qt 前缀匹配兼容版本号变化
策略 3  标题启发式    标题含「微信/WeChat/Weixin」且尺寸 ≥ 400×300
```

类名匹配实现（前缀匹配兼容 Qt 版本号）：

```python
KNOWN_CLASS_EXACT = {
    "WeChatMainWndForPC",      # 微信 3.x（Duilib）
    "WeChatMainWnd",
    "Qt51514QWindowIcon",      # 微信 4.1.13 实测
    "mmui::MainWindow",
}
KNOWN_CLASS_PREFIX = ("Qt", "WeChat", "Weixin")
```

### 4.2 截图：DPI 一致性（踩坑重点）

**问题**：客户区 `1920×1030` 被算成 `2400×1287`，远超 1920×1080 屏幕，截出大片黑边且内容错位。

**根因**：DPI 感知级别不一致导致坐标语义混乱。

| 进程 DPI 感知 | Win32 API 返回 | 是否需要手动乘 `dpi/96` |
|---|---|---|
| 不感知 | 逻辑坐标（被系统缩放） | 需要 |
| 感知 | **物理像素** | **不需要** |

原代码调了 `SetProcessDpiAwareness(2)` 之后**又乘了一次 1.25**，双重缩放。

**修复**：统一声明 DPI 感知，此后**不再做任何手动缩放**，逻辑唯一。

```python
def ensure_dpi_aware():
    """把本进程声明为「每显示器 DPI 感知」（幂等，只需一次）。"""
    ctypes.windll.shcore.SetProcessDpiAwareness(2)   # PER_MONITOR_DPI_AWARE
```

**另改用 `GetClientRect` 替代 `GetWindowRect`**：

- `GetWindowRect` 含边框/阴影，最大化时返回 `(-9,-9,1929,1039)` 这类带负坐标的矩形
- `GetClientRect` + `ClientToScreen` 精确得到内容区

```python
rc = wintypes.RECT()
user32.GetClientRect(hwnd, ctypes.byref(rc))
pt = wintypes.POINT(rc.left, rc.top)
user32.ClientToScreen(hwnd, ctypes.byref(pt))
# 此时 (pt.x, pt.y, w, h) 已是物理像素，直接使用
```

### 4.3 聊天区裁剪：基准等比换算

微信 4.x 客户区布局（1920×1030 实测，逐像素标注）：

```
x: 0 ── 378 ──────────────── 1168 ── 1920
   [ 会话列表 ] [      聊天消息区      ] [右侧留白]
y: 0 ── 86 ──────────── 488 ──── 1030
   [标题栏] [   消息区   ] [输入框区]
```

按基准等比换算，适配不同窗口尺寸：

```python
REF_W, REF_H = 1920, 1030
REF_LEFT, REF_TOP, REF_RIGHT, REF_BOTTOM = 378, 86, 1168, 488

sx, sy = w / REF_W, h / REF_H
left, top = int(REF_LEFT * sx), int(REF_TOP * sy)
right, bottom = int(REF_RIGHT * sx), int(REF_BOTTOM * sy)
```

**越界兜底**：裁剪结果 < 60×60 时退回整幅截图，宁可多识别也不裁出空图。

实测各分辨率自适应效果：

| 客户区尺寸 | 裁剪结果 |
|---|---|
| 1920×1030 | 790×402 |
| 1440×900 | 593×351 |
| 2560×1400 | 1053×547 |

### 4.4 OCR 引擎：必须显式指定中文（踩坑重点）

**问题**：中文识别不出来，只剩英文片段。

**根因**：系统默认引擎是「用户配置语言」，实测为 **英语**：

```
language_tag = en-US          ← 默认引擎是英语！
zh-Hans-CN   → 可用            ← 中文引擎其实装好了
```

用英文模型识别中文 → 中文全部丢失。

**修复**：**优先显式创建中文引擎**，失败才退回默认。

```python
PREFERRED_LANGS = ("zh-Hans-CN", "zh-CN", "zh-Hans", "zh-Hant-TW", "en-US")

for tag in PREFERRED_LANGS:
    lang = Language(tag)
    e = _OcrEngine.try_create_from_language(lang)
    if e is not None:
        return e, tag
```

若最终引擎非中文，会输出告警提示用户安装中文语言包。

### 4.5 异步：单一事件循环（踩坑重点）

**问题**：`RuntimeError: asyncio.run() cannot be called from a running event loop`

**根因**：在 `async` 函数内部又调用了 `asyncio.run()`，形成嵌套。

**修复**：把所有 WinRT `await` 串在**同一个**协程里，外层统一驱动。

```python
async def _recognize_async(img, engine):
    data = _png_bytes(img)
    stream = _InMemoryRandomAccessStream()
    writer = _DataWriter(stream)
    writer.write_bytes(data)
    await writer.store_async()
    await writer.flush_async()
    stream.seek(0)

    decoder = await _BitmapDecoder.create_async(stream)
    bitmap = await decoder.get_software_bitmap_async()
    return await engine.recognize_async(bitmap)
```

并加 `_run_coro` 兜底：若当前线程已有事件循环，则另起线程执行，避免嵌套报错。

### 4.6 中文分词重建（踩坑重点）

**问题**：中文引擎把每个汉字识别成独立 word，直接取 `line.text` 得到畸形文本。

| 修复前 | 修复后 |
|---|---|
| `微 信 单 条 消 ， 巒 制 探 针 ． e × e` | `微信单条消，巒制探针．e×e` |
| `（ 上 海 阶 跃 星 辰 ] Step Pla` | `（上海阶跃星辰] Step Pla` |
| `微 信 电 脑 版` | `微信电脑版` |

**修复**：按相邻 word 的 `bounding_rect` 水平间距判断是否补空格。

```python
if _is_cjk(prev_t[-1:]) and _is_cjk(t[:1]):
    need_space = False        # 汉字/全角标点之间不插空格
else:
    ref_h = char_h or prev_char_h or 12.0
    need_space = gap > ref_h * 0.3    # 英文单词间按间距补空格
```

`_is_cjk` 覆盖范围：CJK 统一表意文字、扩展 A、CJK 标点、全角字符、兼容表意文字。

| # | 问题 | 现象 | 修复 |
|---|---|---|---|
| 1 | 类名硬编码 | 微信 4.x 检测不到窗口 | 三级降级定位 |

| 10 | 全局搜索越界 | 抓到桌面的 `SysListView32`、其它进程的 `EditControl` | 限定在微信窗口子树内搜索 |
| 11 | `winsdk` 构建失败 | Python 3.13 无预编译 wheel | 改用 `winrt-*` 分包 |
| 12 | 新旧 API 命名差异 | — | 新版为 **snake_case**（`recognize_async`） |

## 六、依赖说明

### 6.1 安装

```bash
pip install winrt-runtime winrt-Windows.Media.Ocr winrt-Windows.Globalization \
            winrt-Windows.Graphics.Imaging winrt-Windows.Storage.Streams \
            winrt-Windows.Foundation
```

### 6.2 为什么不用 `winsdk`

`winsdk` 在 **Python 3.13 上没有预编译 wheel**，安装会失败：

```
ERROR: Failed building wheel for winsdk
ERROR: Failed to build installable wheels for some pyproject.toml based projects (winsdk)
```

新版 `winrt-*` 分包提供 cp313 wheel，可直接安装。

### 6.3 API 命名差异（重要）

| | 旧 `winsdk` | 新 `winrt-*` |
|---|---|---|
| 命名风格 | PascalCase | **snake_case** |
| 识别 | `RecognizeAsync` | `recognize_async` |
| 解码 | `CreateAsync` | `create_async` |
| 位图 | `GetSoftwareBitmapAsync` | `get_software_bitmap_async` |
| 查询语言 | `GetAvailableRecognizerLanguages` | **不存在**（需自行枚举尝试） |

### 6.4 系统要求

- Windows 10 / 11
- **中文 OCR 语言包**：设置 → 时间和语言 → 语言 → 中文 → 可选功能 → 光学字符识别

缺失时程序会记录告警并降级为「无上下文润色」，不影响润色与回填。

## 八、验证结果

### 8.1 OCR 端到端实测

对真实微信截图识别输出：

```
（上海阶跃星辰] Step Pla
微信单条消，巒制探针．e×e
微信电脑版
sk-●●●●●●●●（已脱敏，原为一条 40+ 位的密钥）
08：55
```

中文、英文、URL、文件名均可识别。

> 注：上例中的密钥已脱敏。OCR 会把聊天里出现的任何凭据一并识别出来，
> 因此**不要把 OCR 原始输出直接贴进文档或提交到版本库**。

### 8.2 OCR 精度说明

OCR 存在**固有识别误差**（图像识别而非读取文本）：

| 原文 | 识别结果 |
|---|---|
| `消息复制` | `消，巒制` |
| `invite` | `invte` |

因此上下文用于给模型「了解对话语境」，**不必逐字精确** —— 大模型能容忍此类噪声。若需精确文本，应引导用户手动粘贴。

## 九、兼容性矩阵

### 9.1 3.x 兼容性说明（**未实测**）

**3.x 未在真机验证**，结论来自代码走查与 UIA 行为推断。已知需注意：

1. **输入框定位依赖「最靠下」语义**：微信 3.x 的顶部搜索框与底部消息输入框 `Name` 均为空，原实现靠「取最靠下的 Edit」区分。改造后已**限定在微信窗口子树内**搜索，保持该语义。

2. **消息列表可能选错**：3.x 的**会话列表与消息列表都是 `ListControl`**。当前用「子项最多」启发式选择，消息多时通常正确，但**消息少而会话多时可能选错**。原实现用 `Name="消息"` 精确匹配更稳，建议改为「先按 Name 精确匹配，再回落子项数量」。
