## 1. 概述

### 1.1 背景与目标

- **要解决的问题**：微信 4.x 客户端用 Qt 重写后**完全不向 Windows UI Automation 暴露内部控件**，
  导致「读取当前聊天最近若干条消息作为润色上下文」这一能力在 4.x 上失效。
  实测证据：主窗口 `GetChildren()` 恒为 0；主动发 `WM_GETOBJECT` 唤醒多轮仍为 0；
  消息区 `Ctrl+A/C` 复制到 0 字符。因此 4.x 用户只能做「无上下文润色」。
- **预期效果**：微信 4.x 用户按热键后能自动获得**大致准确的聊天上下文**，润色质量与 3.x 相当；
  且**微信 3.x 的全部现有行为零变化**。
- **涉及终端**：Windows 10/11 64 位桌面端（本程序为 PyInstaller 打包的桌面助手，并以 Inno Setup 分发）。

### 1.2 范围与边界

- **本次做**：
  - 聊天上下文读取从「单一 UIA 直读」升级为**三级降级**：UIA 消息列表直读 → UIA 控件树扁平收集 → OCR 截屏识别
  - 新增**截屏识别模块**：客户区截图 + 聊天区等比裁剪 + Windows 内置 OCR + 中文行文本重建
  - 微信窗口定位增强：新增「消息列表定位」「控件树文本收集」「进程运行判断」；
    输入框定位扩展为同时支持编辑框与文档控件，并保持「窗口子树内最靠下」语义
  - 新增配置开关 `ocr_context`（默认开启）
  - 提示文案分类细化，新增「检测到微信运行但主窗口未定位」提示
  - 依赖声明与打包配置同步（新增 OCR 运行时）
- **本次不做**（明确排除）：
  - 读取微信本地数据库 / 解密聊天记录（加密、违反 ToS、维护成本高）
  - 进程注入 / 内存分析（高风险、易触发风控与杀软）
  - 调用视觉大模型做 OCR（需额外 Key 与费用；Windows 内置 OCR 已够用）
  - 自动右键菜单复制批量读取整段会话（需逐条定位消息，且属独立课题）
  - 修改 3.x 的读取精度来源（3.x 必须继续走文字精确的 UIA 直读）
- **依赖方**：
  - Windows 10/11 内置 OCR 引擎（`Windows.Media.Ocr`）
  - 系统**中文「光学字符识别」可选功能**（语言包），缺失时降级
  - Python 侧 `winrt-*` 分包绑定（Python 3.13 无 `winsdk` 预编译包）

### 1.3 术语定义

| 术语 | 说明 |
|------|------|
| UIA | Windows UI Automation，无障碍接口；程序借此读取其它应用的控件树 |
| QAccessible | Qt 的无障碍桥；微信 4.x 该构建未启用，故 UIA 看不到子控件 |
| 客户端区 / 客户区 | 窗口去除标题栏与边框后的内容区域，是截图的目标范围 |
| 聊天消息区 | 客户区内「左侧会话列表右侧、底部输入框上方」的消息显示区域 |
| 三级降级 | 读上下文时按可靠性依次尝试三种手段，前者失败才进入后者 |
| 能力探测 | 用「运行时能否找到消息列表/输入框」决定走直读还是截屏识别，**不解析微信版本号** |
| 基准等比换算 | 以 1920×1030 客户区为基准录制聊天区边界，按实际客户区尺寸等比缩放 |
| 词距重建 | 中文 OCR 会把每个汉字输出为独立词，需按相邻词框水平间距重新拼接成行 |

## 2. 系统交互

### 2.1 上下文图

```
┌──────────────┐                    ┌─────────────────────────┐
│  用户        │                    │  微信 AI 润色助手        │
│  (按热键)     │───────────────────▶│                         │
└──────────────┘                    │  ┌───────────────────┐  │
                                    │  │ 上下文读取（降级链）│  │
┌──────────────┐                    │  └─────────┬─────────┘  │
│  微信客户端   │◀───定位/置前/键盘──│            │            │
│  3.x / 4.x    │────画面（截图）───▶│            │            │
└──────────────┘                    │  ┌─────────▼─────────┐  │
                                    │  │ Windows 内置 OCR   │  │
┌──────────────┐                    │  └───────────────────┘  │
│  大模型 API   │◀───草稿+上下文─────│                         │
│ (DeepSeek)   │────多个候选版本───▶│                         │
└──────────────┘                    └────────────┬────────────┘
                                                 │ 回填（Ctrl+A/V）
                                                 ▼
                                            微信输入框
```

要点：截图与识别**全部在本机内存完成**，不上传；上传给大模型的只有「草稿 + 识别出的上下文文本」。

### 2.2 核心流程

```
用户          助手主流程          微信窗口          降级链              OCR
 │                │                  │                │                  │
 │ 按热键         │                  │                │                  │
 │───────────────▶│ 轮询定位窗口      │                │                  │
 │                │─────────────────▶│                │                  │
 │                │◀──── 找到窗口 ────│                │                  │
 │                │ 读上下文          │                │                  │
 │                │─────────────────────────────────▶│                  │
 │                │                  │                │ ① 消息列表直读    │
 │                │                  │◀───────────────│  (3.x 命中即返回) │
 │                │                  │                │ ② 控件树扁平收集  │
 │                │                  │                │ ③ 截屏识别        │
 │                │                  │                │─────────────────▶│
 │                │                  │◀── 置前+客户区截图 ────────────────│
 │                │◀──────────── 上下文文本 ──────────│                  │
 │                │ 采集输入框草稿（Ctrl+A/C）          │                  │
 │                │ 调用大模型生成多版本                │                  │
 │                │ 用户选一版 → 回填（Ctrl+A/V）       │                  │
 │◀───────────────│                  │                │                  │
```

关键决策分支（对应第 4 章 BR 规则）：

```
找到窗口？
 ├─ 否 → 区分「未检测到微信」/「检测到进程但未定位到窗口」两类提示，结束
 └─ 是 → 能定位消息列表？ ──是→ UIA 直读（3.x，文字精确）
                          └─ 否 → 控件树能收集到 ≥2 段文本？ ──是→ 扁平收集兜底
                                                             └─ 否 → 截屏识别开关开启且 OCR 可用？
                                                                      ├─ 是 → OCR 读取聊天区
                                                                      └─ 否 → 空上下文（降级为无上下文润色）
```

## 3. 接口契约

> 本产品为桌面工具，无 HTTP 接口。此处描述**对外可观测契约**：配置项、提示分类、日志约定。

### 3.1 配置项契约（`config.json`）

| 字段 | 类型 | 默认 | 说明 | 新增/修改 |
|------|------|------|------|-----------|
| `ocr_context` | Boolean | `true` | 微信 4.x 是否允许用截屏识别读取聊天上下文；`false` 则 4.x 读不到上下文 | 新增 |
| `context_messages` | Integer | `5` | 读取最近多少条消息作为上下文 | 沿用 |
| `grab_timeout` | Integer | `10` | 触发后等待/重试获取微信内容的最长秒数，超时才提示 | 沿用 |
| `console_log` | Boolean | `true` | 是否控制台实时输出日志 | 沿用 |
| `log_prompt` | Boolean | `true` | 是否记录完整提示词与响应原文 | 沿用 |

> 配置读取路径与提示词管理逻辑保持不变（分发版仍写入用户目录，不随临时目录丢失）。

### 3.2 用户可见提示契约

| 编号 | 触发条件 | 提示要点 | 处理建议 |
|------|----------|----------|----------|
| MSG-001 | 超时且未检测到微信 | 未检测到微信窗口 | 先打开微信并进入聊天窗口，再按热键 |
| MSG-002 | 超时但检测到微信进程 | 检测到微信运行，但未定位到主窗口 | 把窗口从最小化/托盘恢复后重试；仍失败则反馈诊断报告 |
| MSG-003 | 定位成功但草稿与上下文皆为空 | 无法生成 | 在输入框写草稿；确认聊天窗口已打开、消息可见 |
| MSG-004 | 大模型调用失败（如 401） | 润色失败及原因 | 检查 API Key / 网络 |

### 3.3 日志契约（`polish.log`）

| 关键日志 | 含义 | 用途 |
|----------|------|------|
| `OCR 状态: OCR 可用（识别语言 xx）` | 启动时探测的 OCR 可用性与识别语言 | 判断是否需要装中文 OCR 语言包 |
| `OCR 后端不可用（原因）` | 依赖缺失或语言包缺失 | 定位降级原因 |
| `消息列表已定位（按名称）: '消息'` | 3.x 走直读 | 确认 3.x 未降级 |
| `读取到 N 条聊天上下文（UIA 列表模式）` | 直读成功 | 确认 3.x 行为不变 |
| `读取到 N 条聊天上下文（UIA 扁平模式…）` | 扁平收集成功 | 过渡版本兜底生效 |
| `读取到 N 条聊天上下文（OCR 截屏模式）` | 截屏识别成功（4.x 路径） | 确认 4.x 适配生效 |
| `聊天区裁剪: 客户区 WxH → 区域 (…)-(…) 尺寸 WxH` | 裁剪区域与尺寸 | 核对不同窗口尺寸下裁剪是否落在消息区 |
| `未读取到任何聊天上下文` | 三级全部落空 | 已正常降级 |

> **日志不记录聊天正文**：OCR 只记录识别行数，不输出识别到的文字内容。

### 3.4 模块间契约（代码层约定，供开发对齐）

| 契约 | 说明 | 兼容要求 |
|------|------|----------|
| `read_wechat_recent(n, use_ocr=True, hwnd=None)` | 上下文读取唯一入口，内部三级降级 | 新增参数均有默认值，旧调用方式仍可用 |
| `wechat_window` 公开函数 | 窗口定位/输入框聚焦等既有函数 | **只增不删**，签名与语义保持稳定，保护回填模块与诊断探针 |
| `ocr_reader.read_chat_context(hwnd, max_messages)` | OCR 读取入口，失败/不可用返回空串 | 全链路不抛异常 |

## 4. 业务规则

### 4.1 降级与选择规则

| 编号 | 规则 | 触发时机 | 不满足时行为 |
|------|------|----------|--------------|
| BR-001 | 3.x 优先命中：能按名称（`消息`/`ChatView`）或启发式定位到消息列表，则**只用 UIA 直读** | 每次读取上下文 | 进入 BR-002 |
| BR-002 | 定位不到消息列表时，才允许「控件树扁平收集」；且收集到的文本段数需 ≥2 段才认定有效 | BR-001 未命中 | 进入 BR-003 |
| BR-003 | 前两级皆落空，且 `ocr_context=true` 且 OCR 后端可用，才执行截屏识别 | 前两级未命中 | 返回空上下文（无上下文润色） |
| BR-004 | **不做微信版本号判断**：一律以运行时能力探测决定路径 | 每次读取上下文 | — |
| BR-005 | 任一环节异常均不得向外抛出，统一记录日志后返回空串 | 全过程 | 主流程继续（草稿捕获、AI 调用、回填不受影响） |

### 4.2 截屏与裁剪规则

| 编号 | 说明 | 逻辑 | 示例 |
|------|------|------|------|
| BR-101 | 截图范围取**客户区**（不含标题栏/边框） | `GetClientRect` + `ClientToScreen` 转屏幕坐标 | 最大化窗口返回 `(0,-2,1920,1020)`，而非含负坐标的 `(-9,-9,1929,1039)` |
| BR-102 | 进程声明**每显示器 DPI 感知**且仅声明一次；声明后不再做任何手动缩放 | 幂等声明 | 避免 1920×1030 被算成 2400×1287 导致黑边错位 |
| BR-103 | 聊天区按基准 1920×1030 的边界（左 378 / 上 86 / 右 1168 / 下 488）**等比换算** | `sx=w/1920, sy=h/1030` | 1920×1030→790×402；1440×900→593×351；2560×1400→1053×547 |
| BR-104 | 裁剪结果越界则钳制；**小于 60×60 时退回整幅客户区截图** | 保底不裁空图 | 60×40 客户区→退回整幅 |
| BR-105 | 截图前置前目标窗口，避免截到遮挡内容 | — | 置前后等待短暂稳定再截 |

### 4.3 识别与文本重建规则

| 编号 | 说明 | 逻辑 | 示例 |
|------|------|------|------|
| BR-201 | **必须优先创建中文识别引擎**（`zh-Hans-CN` 等），失败才退回系统默认语言 | 依次尝试语言标签 | 系统默认为 `en-US` 时中文会整体丢失 |
| BR-202 | 最终引擎非中文时记录告警并提示安装语言包 | — | 提醒「设置→语言→中文→光学字符识别」 |
| BR-203 | **中文逐字重建**：相邻词两侧均为中日韩文字/全角标点时**不插空格**；否则按间距超过约 0.3 倍字高补空格 | 依据词边框水平间距 | 修复前 `微 信 单 条 消 息` → 修复后 `微信单条消息` |
| BR-204 | 过滤噪声行：不含任何字母/数字/汉字的行丢弃（图标、分隔线误识别） | — | `————` 丢弃 |
| BR-205 | 去除相邻重复行；取最后 N 行作为上下文 | N=`context_messages` | — |
| BR-206 | OCR 识别存在**固有误差**，上下文仅用于让模型理解语境，不作为逐字依据 | — | 「消息」可能识别为「消，」 |

### 4.4 兼容性规则

| 编号 | 规则 | 说明 |
|------|------|------|
| BR-301 | 微信 3.x 的读取来源与精度**不得改变**：仍走 UIA 直读，不因引入 OCR 而改用识别结果 | 实测 3.x `use_ocr=true/false` 结果完全一致 |
| BR-302 | 输入框定位保持「窗口子树内最靠下」语义，且优先只枚举编辑框，仅当编辑框为空时才回退文档控件 | 保护 3.x 顶部搜索框与底部输入框的区分逻辑 |
| BR-303 | 4.x 输入框聚焦继续使用**坐标点击兜底**（UIA 拿不到控件），不得删除 | 键盘操作不依赖控件树 |
| BR-304 | 窗口定位与输入框搜索**限定在微信窗口子树内**，禁止全局搜索 | 避免误选桌面列表控件或其它进程的输入框 |
| BR-305 | 微信缩在托盘时判定为「进程在运行」 | 便于给出「恢复窗口」而非「先开微信」的提示 |

| 尝试截屏识别 | 识别到文本 | 完成(OCR) | ✅ |

## 6. 非功能需求

### 6.1 性能指标

- **不新增热路径开销**：3.x 在降级链第一级命中即返回，**不触发截图与识别**。
- **OCR 仅在必要时触发一次**：仅当 UIA 两种手段都落空（即 4.x 场景）才执行，且每次读取只截一次图。
- 实测参考值（本机 1920×1080 @ 客户区 1920×1022）：
  - 截图 + 裁剪：**< 0.4s**
  - 单次 OCR 识别（含 WinRT 异步驱动）：**约 0.4 ~ 0.7s**
  - OCR 引擎创建：进程内一次性，结果缓存复用
- **识别区域受限**：只识别聊天消息区（1920 基准下 790×402），并限制返回条数，控制算力。

### 6.2 安全约束

- 截图与识别**全程本地**，不联网、不上传、不落盘。
- 日志**不记录聊天正文**，仅记录行数与区域尺寸。
- 不读取、不解密微信本地数据文件；不注入进程；不模拟发送消息（只回填到输入框，发送由用户决定）。
- 敏感信息（API Key）不写日志。

### 6.3 兼容性

- **向前兼容（关键）**：微信 3.x 的窗口定位、消息列表直读、输入框聚焦、草稿捕获、回填、
  提示词配置、日志与首次引导等全部行为保持不变；新增能力只在 3.x 路径落空后才生效。
- **接口兼容**：`wechat_window` 既有公开函数签名与语义稳定，回填模块与各诊断探针
  （环境诊断、控件树探测、剪贴板探针、单条消息复制探针）无需改动即可继续使用。
- **降级兼容**：未安装 OCR 依赖或未安装中文语言包的环境，程序可正常启动，
  自动降级为「无上下文润色」，不崩溃、不阻塞、不误发按键。
- **存量配置**：`config.json` 无需迁移，缺失 `ocr_context` 时按默认值（开启）处理。

## 8. 上线策略

### 8.1 灰度方案

- 灰度维度：**按人（分发对象）**——本工具为单机桌面程序，按用户分发，不做服务端灰度。
- 灰度步骤：
  1. 先在本机（微信 3.x）完成全链路回归，确认 3.x 无回归；
  2. 交付给微信 4.x 用户安装，先验证「窗口定位 + OCR 读取 + 回填」三步；
  3. 观察其 `polish.log` 中的关键日志行，确认走的是预期路径；
  4. 全量分发。

### 8.2 回滚方案

- 回滚方式：**配置开关**（首选）+ **程序包回滚**（兜底）
  - 配置级：把 `ocr_context` 置为 `false`，立即跳过截屏识别（无需换包）；
  - 代码级：回滚到上一版程序包/安装程序（本改动不涉及数据迁移，回滚无副作用）。
- 回滚影响：4.x 恢复为「无上下文润色」；3.x 不受任何影响。
- 回滚验证：3.x 按热键仍走 UIA 直读并读到 N 条；4.x 不崩溃、正常提示。

### 8.3 监控告警

- 关键指标（日志可观测，无服务端监控）：
  - 「OCR 状态」行是否存在且为可用
  - 读取模式分布（UIA 列表 / UIA 扁平 / OCR / 空）
  - 出现「未读取到任何聊天上下文」的频次
  - 待选：记录单次读取耗时
- 告警阈值：单机场景不做自动告警；由用户反馈「读不到上下文」时按日志判定原因。

## 9. 附录

### 9.1 关键踩坑与结论（实现期实测）

| # | 问题 | 现象 | 处理 |
|---|------|------|------|
| 1 | 微信 4.x 不暴露 UIA | 子控件恒为 0；`WM_GETOBJECT` 唤醒无效 | 放弃 UIA，改用截屏识别；同时保留唤醒调用（对 3.x 无害） |
| 2 | **同线程内 UIA + WinRT OCR 死锁** | 同一线程先做 UIA 再 OCR（或反之）会**卡死 45s+ 无返回** | **OCR 协程一律放到独立线程执行**（本次最关键修复） |
| 3 | OCR 默认引擎为英文 | 中文整段丢失，仅剩英文片段 | 优先显式创建中文引擎 |
| 4 | 中文逐字空格 | `微 信 单 条 消 息` | 按词框水平间距重建行文本 |
| 5 | DPI 重复缩放 | 客户区 1920×1030 被算成 2400×1287，截出黑边错位 | 声明每显示器 DPI 感知且只声明一次，之后不再手动缩放 |
| 6 | `GetWindowRect` 含边框 | 最大化时返回负坐标与黑边 | 改用客户区矩形 |
| 7 | 全局搜索控件越界 | 误捞桌面列表控件、其它进程输入框 | 一律限定在微信窗口子树内搜索 |
| 8 | 3.x 消息列表可能误选 | 会话列表与消息列表同为列表控件 | **先按名称精确匹配，再回落启发式** |
| 9 | `winsdk` 在 Python 3.13 无法构建 | 安装失败 | 改用 `winrt-*` 分包；另需补 `Foundation.Collections` |
| 10 | 打包后 OCR 不可用 | 惰性导入易被静态分析漏掉 | 打包配置显式收集 winrt 子模块与原生库 |
| 11 | 未装 OCR 依赖时不能崩 | — | 全链路惰性加载 + 异常吞掉 + 返回空串 |
| 12 | **草稿捕获模块缺少键盘模拟库导入（存量缺陷）** | `capture_draft` 内部抛 `NameError` 被 `except` 静默吞掉，导致**恒返回空草稿**；3.x 因可直读输入框而不易暴露，**4.x 必然读不到草稿**（草稿是润色核心） | 补回键盘模拟库导入；改为可观测的异常日志，避免再次被静默吞掉 |
